The link still works.
The claim doesn’t.

You cited a page. Months later the page changed a number. No link died, no build broke, nothing told you — and your documentation now says something false with a citation attached.

claimrot re-reads the sources you cite and reports the claims that stopped being true.

Four answers, not two

Most monitors diff a page against its last snapshot and tell you same or changed. That works until the checker itself goes blind. A redesign moves the price, a selector stops matching, and a two-answer system confidently reports that the operator deleted it.

That is the failure claimrot exists to avoid, so it refuses to answer with only two.

HOLDS
The source still says what you published.
DRIFTED
The value changed. You get the old one, the new one, and the URL.
MOVED
Still true, but not where you cited it. You get the new URL.
UNVERIFIABLE
We could not read it, and we will not guess.

When extraction comes back empty, claimrot does not conclude the value is gone. It asks Bright Data Scraper Studio to repair the scraper, runs it again, and then looks for the value elsewhere on the same site — following the site’s own links and sitemap, never a search engine and never another host. Only when a working scraper finds it nowhere does it report REMOVED. Healing is not what makes it fast. It is what makes a negative believable.

How a check runs

  1. Reduce the claim, once

    A model reads your prose claim a single time and reduces it to something testable — a value, a unit, and the label on the page that governs it. After that the model is never called again for that claim.

  2. Look for the label, never the value

    A price that moved from the “Adult” row to the “Senior” row is still on the page. Searching for the number finds it and calls the claim fine, forever. claimrot searches for the label and reads whatever now sits beside it.

  3. Heal on blindness, never on change

    Finding nothing is not evidence of absence — it is a statement about our own eyesight. So an empty result triggers a repair of the scraper, and then a look one page over, before it is allowed to become a verdict.

  4. Report with receipts

    Every verdict carries what you published, what the page says now, the URL, and why the two disagree. Nothing asks you to take its word.

Quickstart

Node 22 or newer. An Anthropic API key is needed for ingest only.

git clone https://github.com/claimrot/claimrot
cd claimrot && npm install

# Reduce prose claims into testable assertions. Once per claim.
npm run cli -- ingest 'path/to/*.facts.json'

# Fetch each source, resolve candidates, heal on blindness, record verdicts.
npm run cli -- check

# Print the drift receipts.
npm run cli -- report

In continuous integration

Emit verdicts as JSON and let the action fail the pull request when a cited claim has drifted. 

npm run cli -- report --json > claimrot-verdicts.json
- uses: claimrot/claimrot@v1
  with:
    verdicts: claimrot-verdicts.json
    confidence-floor: "0.75"

UNVERIFIABLE never fails a build. A check that turns red because our own scraper broke gets switched off within a fortnight, and then it protects nobody.

What it can’t do

Worth knowing before you rely on it. The full list lives in the README.

  • The generic fallback detects blindness but cannot repair itself. Healing needs a real Scraper Studio collector, so self-repair reaches the hosts you have provisioned one for.
  • Claims are checked one at a time rather than one fetch per page, so a page cited by several claims is fetched several times.
  • Relocation searches the cited page’s own links and the host’s sitemap, and stops after five candidates. A value moved somewhere neither of those points to still reads as REMOVED.
  • It verifies a claim against the source it cites. It has no opinion on whether that source was right in the first place.
